# EKE Independent Verification
# Independent Verification Baseline v0.1

## 1. Status

DESIGNED — INDEPENDENT VERIFICATION CONTRACT

This document defines the normative baseline for independent
verification within EKE Open Review.

It does not itself constitute an independent verification result.

## 2. Purpose

Independent Verification is a distinct verification layer used to
determine whether a declared subject satisfies explicitly defined
verification criteria based on identifiable evidence and recorded
procedures.

Independent Verification must remain separate from:

- review registration
- certificate issuance
- NFT representation
- registry state
- accreditation
- certification authority

## 3. Core Principle

No verification determination may exceed:

- declared scope
- applicable criteria
- available evidence
- executed procedures
- observed results
- reproducibility requirements
- stated limitations

## 4. Independence

Where independent verification is claimed, the verification record
must explicitly identify:

- verifier reference
- independence declaration
- conflict-of-interest status
- applicable independence conditions
- evidence supporting the independence determination

Independence must not be inferred merely from the label "independent".

## 5. Verification Dimensions

Independent Verification may evaluate:

- implementation verification
- test verification
- independent reproduction
- multi-implementation verification
- evidence consistency
- traceability
- procedural conformity

Each dimension must be independently recorded.

A dimension must not be inferred from another dimension.

## 6. Evidence Boundary

Every verification determination must identify the evidence boundary.

Evidence must have traceable identifiers.

Evidence availability alone does not establish verification.

## 7. Verification Procedure

A verification record must identify:

- verification procedure
- applicable criteria
- evidence references
- execution information
- observed results
- determination
- limitations

## 8. Reproduction

Where reproduction is applicable, the record must identify:

- artifact reproduced
- reproduction procedure
- reproduction environment
- reproduction result
- reproduction evidence

Successful reproduction must not be inferred without recorded results.

## 9. Multi-Implementation Verification

Where multi-implementation verification is claimed, the record must identify:

- implementation references
- applicable common criteria
- execution results
- comparison method
- comparison result

Agreement between implementations must be established from recorded
results rather than assumed.

## 10. Determination States

The Independent Verification record may represent:

- DESIGNED
- EXECUTED
- DETERMINED
- CHALLENGED
- REVOKED

The state alone must not establish a substantive verification claim.

## 11. Verification Outcomes

Verification outcomes are distinct from lifecycle state.

Supported outcomes:

- PASS
- PARTIAL
- FAIL
- NOT_DETERMINED

An outcome must be supported by applicable criteria and evidence.

## 12. Independence Status

Supported independence states:

- NOT_APPLICABLE
- DECLARED
- SATISFIED
- FAILED

## 13. Reproduction Status

Supported reproduction states:

- NOT_APPLICABLE
- NOT_PERFORMED
- REPRODUCED
- FAILED

## 14. Multi-Implementation Status

Supported multi-implementation states:

- NOT_APPLICABLE
- NOT_PERFORMED
- SATISFIED
- FAILED

## 15. Traceability

Independent Verification must remain traceable to:

Review
→ Scope
→ Evidence
→ Procedure
→ Observed Result
→ Determination
→ Verification Record

## 16. Negative Constraints

The following must not be inferred solely from the existence of an
Independent Verification record:

- certification
- accreditation
- regulatory approval
- scientific validity
- security certification
- production readiness
- cryptographic assurance

unless separately established through identifiable authority and evidence.

## 17. AI Assistance

AI assistance must be explicitly disclosed where used.

AI assistance must not silently become an independent human
determination.

## 18. Change Control

Changes to this baseline must be:

1. Explicitly identified.
2. Versioned.
3. Traceable.
4. Reviewed for architectural impact.
5. Tested where implementation is affected.

## 19. Current State

DESIGNED

Executable implementation, verification records, conformance tests,
and independent reproduction artifacts are separate implementation
concerns.
